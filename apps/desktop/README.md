# Corch DSH desktop for Windows

English | [中文](README.zh.md)

Desktop startup resolves shipped plugins directly from the portable runtime; it does not create symbolic links or junctions in `data`. Administrator privileges and Windows Developer Mode are not required. Keep the existing `data` folder when replacing the program, including after a failed startup. Existing profile manifests, patches, credentials, sessions and additional plugin directories are preserved.


Copy controls can write links and invitation codes to the clipboard from the local workbench. Web pages receive no clipboard-read permission.


## Use the portable client

Windows 10/11 x64 is required. Extract the entire ZIP into a writable folder, then double-click **Corch DSH.exe**. Node.js, Electron, the Web interface, the expert interview plugin and the patched better-sidebar provider are included; no system installation or pnpm download occurs at startup.

The client creates its own `data` folder beside the executable. It stores the Electron browser profile, DSH settings/credentials, sessions, a working directory and logs there. Keep this folder when replacing the program. Treat it as private; do not upload it with bug reports. Do not run multiple copies against the same data directory. `Corch DSH.exe --data-dir C:\absolute\private-folder` selects a separate profile. Do not point this option at an existing browser or DSH home.

Configure the question-generation model through the existing Models and credential services. Separately configure the Worker origin and its administrator-created publishing API Key under interview settings; the deployed service origin is `https://114.132.201.209`. The native process encrypts the Key for the current Windows account and sends it only as an Authorization header to the fixed upload endpoint. Remote pages cannot read the Key; browser persistence, URLs, share links and logs never store it. **发布并打开 SPA** uploads and opens immediately without another confirmation or administrator login. Missing, expired or revoked authorization produces an inline settings shortcut. Both Worker and HTTPS reverse proxy must support `/publish/api/`.

Closing the client stops its own local backend. Other DSH installations and services are unaffected. The local HTTP listener binds only `127.0.0.1`, uses an OS-assigned port on first start and retains that port for browser storage continuity. If another program occupies the saved port, startup fails with a log instead of adopting or closing that program. Startup logs are in `data/backend.log`; `data/startup-error.txt` records a launch failure. Microphone permission requires a native confirmation; hardware and real provider quality need separate acceptance.

The application is unsigned and has no automatic updater. Windows may display an unknown-publisher/SmartScreen warning. Electron and Node upstream licenses are included. Obtain updates as complete packages from the operator; verify the published SHA256 before extraction.

## JD research collection

JD candidates are rendered in an isolated persistent browser session, with one shared window per platform. Main windows and popups start with a 1360×860 content area and enforce a minimum content width of 1280. Public originals need no login. Existing platform sessions are reused across searches and restarts; websites can expire them or require verification, and one platform’s login does not authenticate another. External pages have no native interface, and cookies or passwords are never supplied to the model. Preserve `data/electron` and `data/dsh/jd-projects` when moving this client; confirmed HTML reports remain under `data/exports`.

The native collector writes `data/jd-collection-settings.json` on first use. All fields are required when editing it; invalid settings stop collection. `min_interval_ms` defaults to 10000 between platform main-frame navigations; `max_navigations_per_hour` is 12; `max_sources_per_batch` is 20, with excess candidates retained for later collection; `render_settle_ms` is 1500; `cache_ttl_ms` is 86400000. Known recruitment subdomains share a platform budget; other hosts have separate budgets. These limits reduce this client’s activity and cannot guarantee access.

Each candidate is validated independently. An invalid or unsupported URL produces a source-specific reason without failing the batch. Its original position counts toward `max_sources_per_batch`; rejecting it cannot admit extra candidates beyond that limit. Public HTTP, embedded credentials and unsafe protocols remain rejected.

Capture windows display a local loading message until the platform has visible content. Failed loads, empty-page timeouts and platform stops display their reason and a route back to the workbench. Failed opens report failure and stop background access; only an explicit new attempt reloads the source. The local view does not modify the platform page or its login storage. [Native-window acceptance](jd-capture-status.acceptance.mjs) checks these states in Electron using controlled local pages.

Ordinary login windows passively watch DOM changes and navigation, without making probe requests. Once a complete JD is readable, the collector records its original URL, capture time and hash and delivers it to the owning search automatically. It stops after that target succeeds; unrelated subsequent browsing is not automatically archived. A private delivery queue under `data/jd-collection` survives renderer reload and application restart; acknowledgement follows the Host save and closes the matching capture and its child windows. Login, verification, failed saves and newer targets remain open; window closure preserves browser login storage. Preserve that directory with project data when moving the client. Security-verification windows require explicit recovery even when a JD becomes readable. Each successful batch result enters the delivery queue before collection advances, so later slow pages do not delay its project save. The workbench reports Host-saved originals and readable text; these states do not claim that an account is authenticated. Expired-job pages remain unavailable even when they contain recommendations, and cannot supply originals or trigger automatic retries. Zhaopin recognizes its visible offline-status image and reads only its description card. 58 reads the description card and displayed job name, excluding account navigation, company introductions and recommended roles; unrecognized layouts cannot fall back to whole-page text. Earlier extraction caches remain on disk but are not reused. Historical originals and confirmed reports remain unchanged.

Successful rendered originals are cached privately under `data/jd-collection` with SHA-256 and their original acquisition time. A valid cache hit avoids navigation across projects and restarts; expiration does not rewrite capture time. Security challenges and HTTP 429 persist a platform stop in the same directory, including background requests and redirects. A stop survives restart and does not expire automatically. Explicit human verification can open the stopped platform; recovery only reads the current page and clears the stop after a valid JD is found. Cached originals remain available without network access during a stop. Login pages, network errors and non-JD pages are distinguished from anti-bot restrictions.

The [teaching workbench](../../packages/client/ui-polus-teaching-reform/README.md) documents archived searches, source evidence, inference labels and confirmed HTML export. Live compatibility can be checked with [the opt-in platform driver](jd-platforms.acceptance.mjs), which uses the production collector without remote debugging and records state, navigation times and source hashes. [Automatic-save live acceptance](jd-login-live.acceptance.mjs) runs the ordinary desktop and verifies Host persistence without a continuation click, remote debugging or model prompts. Synthetic acceptance does not establish real-site compatibility.

Confirmed HTML exports pass the saved native file path to `shell.openPath`, using the OS `.html` association, including filenames with Unicode, spaces and URL-special characters. An empty launch result means success; a returned error message or rejected promise reveals the saved report in its directory. The OS chooses the registered HTML application. The opt-in `--live-shell` flag on [desktop acceptance](jd-research.acceptance.mjs) invokes actual file and folder handlers; its launch-failure injection tests fallback without changing OS associations.

## Build reference

The desktop assembly and teaching plugin are private workspace packages distributed through the portable client, outside the upstream npm release sequence. Use Windows x64, a supported Node.js release, pnpm11.7.0 and Windows PowerShell/tar. Run the normal repository build, then:

```powershell
pnpm --filter @polus-ai/corch-dsh-desktop run package:win --out C:\build\Corch-DSH
```

The output directory must not exist. The builder verifies pinned official Electron44.7.2 and Node24.18.0 archives, installs production dependencies from the frozen pnpm lockfile in a publication-only workspace mirror under the repository `.tmp` directory outside the output and materializes workspace packages into the portable closure, refuses symlinks and private configuration in the payload, and emits a ZIP, SHA256 and per-file build manifest. Generated package-manager launchers and installation metadata are excluded so build-machine paths are not shipped. Source maps, compiler state and generated debug path labels are omitted from the portable payload. `--cache` selects an archive cache; `--closure` accepts an previously verified frozen desktop closure for offline assembly. That option still checks required built artifacts and scans the payload; the operator must supply the closure from the matching source/lockfile.

`node --test apps/desktop/policy.test.mjs apps/desktop/publisher.test.mjs apps/desktop/publisher-vault.test.mjs` checks popup restrictions, environment isolation and navigation. Desktop acceptance must launch the actual packaged executable with a separate data directory, load the real plugin, exercise the Models page and native publication against an isolated Worker, and verify backend shutdown. A loopback provider fixture verifies routing/credential plumbing only; it does not establish real model quality or microphone acceptance.

The [desktop decision](../../.agents/notes/implemented/feature/2026-10-14-windows-desktop-client.md) owns lifecycle and packaging rationale. The desktop adds no model prompt or tool behavior; existing bundles own those effects.
